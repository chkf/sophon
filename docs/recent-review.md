# Recent 后台整理

服务启动后自动运行，旧配置的 `GATEWAY_RECENT_REVIEW_ENABLED=false` 不再生效。此功能独立于主动消息、静默时间、发送次数和主动渠道开关；不会发送聊天消息。Recent 整理独立使用当前 Provider 的额度，不受主动消息的后台调用开关限制；主动消息本身仍需单独启用。使用当前 Provider，不自动切换。

正式回复送达后约一分钟安排整理，连续消息会合并等待。服务启动时检查未完成的审阅进度；没有新资料时停止等待计时器，下一次交付再唤醒。积压按批处理，两批成功审阅至少间隔一分钟；失败或 Provider 禁止后台调用时至少等待 15 分钟。等待时间持久化，重启不会绕过。API 调用会使用对应服务额度。

整理范围是管理员的正式聊天记录。已绑定的 Telegram 与微信使用同一个会话和审阅进度，只处理一次。先检查 Core 可用，再读取完整消息片段；不把整理结果写回聊天记录，不开放文件、联网、语音、生图或其他业务工具。

模型提出新增、更新或删除 Recent 的 JSON 建议。只保留有明确依据的待接续话题、待跟进事项和待分享内容；稳定事实、偏好及已结束经历交给记忆图；已有记录优先更新，删除仅限重复、被更正或失去保留价值的内容。系统检查字段、数量、目标范围和修订号，再将删除凭据、新增、更新、删除和审阅游标放入同一个 SQLite 事务。任一操作失败则整批回滚；旧建议不能覆盖较新的记录。

每批最多 40 条完整消息，JSON 消息预算 24000 UTF-8 字节；已有 Recent 最多提供 60 条，总预算 12000 字节。超出批次预算的后续消息留待下一次；单条消息超过普通批次预算时，按顺序连续读取，带上之前的累计提案；每次请求的正文与指令合计最多 64000 UTF-8 字节，包含已有 Recent 和累计提案，不截掉消息尾部。全部片段成功、提案校验通过后才一次性提交条目变化与进度；中途失败或跳过时均不提交。长消息可能需要多次模型调用。只能修改本次提供的 Recent 条目。每类变化最多 8 项。

遇到结果不明的 Provider 错误，保留原操作标识，避免绕过付费调用去重。同一批资料最多尝试三份已收到但无效的模型建议，然后等待资料变化或人工检查。故障日志只写固定原因提示，不打印聊天内容、模型正文或文件路径。`gateway_state` 中的 `runtime/recent-review` 保存最近状态和下次可尝试时间；可在停止服务后使用 SQLite 工具查看。

使用 `npm run init` 创建的当前六表数据库可直接启用，无需新增表或迁移聊天。旧数据库仍可正常聊天，后台整理返回 `unsupported_schema`，需先由操作者完成已有数据库迁移流程。Recent 整理与记忆图分类各自运行：建立图引用不会停用 Recent 整理，也不会从上下文目录隐藏这些条目。正文与交流状态仍以 Recent 为准，图中只保留引用。
